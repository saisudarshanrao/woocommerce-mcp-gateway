# Demo video outline

The submission asks the video to cover six areas. This is an order to record
them in, with what to have on screen and the points to make for each. Every
command here has been run against the local cluster. Where a point needs more
than a sentence, the place to read it first is given.

Before recording: `make up`, then `make smoke` and `make chat-smoke`, so that
you know everything works and the model has quota left. Keep two browser
profiles open, one per user, and a terminal.

## 1. System design and implementation

**Show** the diagram at the top of the [README](../README.md), then the
dashboard's Servers page.

**Say**

* Four layers: the store, its MCP server, the gateway with its dashboard, and
  the chat agent. One namespace per concern.
* An admin registers MCP servers once. Every member then uses all of them
  through one endpoint, from an MCP client or from the chat, with their own key
  and without ever seeing an upstream credential.
* The gateway is an MCP client to every upstream and an MCP server to every
  member. Nothing else may call an upstream.

**Then the definition-of-done flow, live, with two users.**
[DEMO.md](DEMO.md) is the script: sections 1 to 5 are the required flow,
section 6 the multi-store bonus, section 7 the other extras.

## 2. Kubernetes

**What runs where**

```bash
kubectl get pods -A | grep -v kube-system
kubectl get secrets -A | grep -vE "kube-system|helm.release"
kubectl get pvc -A
kubectl get ingress -A
```

* Three namespaces: `store-main` (WordPress, MariaDB, the store's MCP server),
  `gateway` (API, dashboard, Postgres, provisioner), `mcp-servers` (two more
  MCP servers). Created stores add `store-<slug>`, hosted servers `mcp-<slug>`.
* Secrets: every credential is generated by its chart into a Secret on first
  install and kept across upgrades. None is in git or in a values file.
* Volumes: the store's database and its `wp-content`, and the gateway's
  Postgres. They survive pod restarts and `helm uninstall`.
* Ingress: two hosts, the store and the gateway. Nothing else has one.

**Requests, limits and probes**

```bash
kubectl get pods -A -o custom-columns='NAMESPACE:.metadata.namespace,POD:.metadata.name,CPU-REQUEST:.spec.containers[0].resources.requests.cpu,MEM-REQUEST:.spec.containers[0].resources.requests.memory,CPU-LIMIT:.spec.containers[0].resources.limits.cpu,MEM-LIMIT:.spec.containers[0].resources.limits.memory' | grep -v kube-system
kubectl -n gateway describe deploy gateway-api | grep -E "Liveness|Readiness|Startup"
```

* Every container states what it needs and the most it may take.
* Readiness says "send me traffic": for the gateway, migrations have run and
  the database answers. Liveness only says "the process is alive", so a slow
  database never gets a healthy pod killed.

**What is public, what is internal, and how that is enforced**

```bash
kubectl get svc -A | grep -v kube-system
kubectl get networkpolicy -A
make isolation-smoke
```

* Every Service is `ClusterIP`: no address outside the cluster. Public means
  "has an Ingress".
* Every namespace denies incoming traffic by default and then allows named
  callers: Traefik to WordPress and the gateway, the gateway's API pods to the
  MCP servers, WordPress to its database.
* Outbound is restricted too: the store's MCP server can reach only its own
  WordPress, the database nothing, and the gateway only DNS, its database, pods
  labelled as MCP servers, and the internet.
* `make isolation-smoke` does not read the policies, it tries each connection.
* Reaching an MCP server is not enough: without its credential it answers 401.

## 3. MCP internals

**Show** [services/gateway/README.md](../services/gateway/README.md), "One tool
call, end to end", and the Audit log page after a call.

**Say: one call from client to store and back**

1. The client sends `tools/call` for `woo__list_orders` to
   `gateway.localhost/mcp` with its API key.
2. Traefik routes `/mcp` to the gateway's API.
3. The gateway hashes the key and looks it up: that is who is calling.
4. It splits the name at `__` into server `woo` and tool `list_orders`, checks
   the server is enabled and reachable and that this role may use the tool.
5. It opens a connection to the store's MCP server with that server's own
   credential, decrypted at that moment, and calls `list_orders`.
6. The MCP server calls WooCommerce's REST API inside the cluster, signing the
   request.
7. The result travels back unchanged, and the gateway writes the audit entry.

**How the gateway connects to upstreams.** A background check every ten
seconds lists each server's tools and keeps the result. Listing tools reads
that, so it never waits on a server. Each call opens its own short connection.

**Collisions, timeouts, a dead upstream.** Show two `server_info` tools side by
side in the tool list; ask the chat to call the sandbox's slow tool for 30
seconds; scale the tasks server to zero and watch the Servers page.

* Names are always `<server>__<tool>`, so two servers' `list_orders` are two
  different names.
* Each server has its own timeout. A slow call fails on its own deadline with a
  sentence saying so, while calls to other servers go through.
* A dead server shows as Unreachable with the reason. The others are
  unaffected, and it reconnects by itself.

Read first: [DESIGN.md](DESIGN.md), "How tool aggregation, routing and failure
handling work".

## 4. Security posture

**Show** an API key being created (shown once), the Servers page as a member
(no address, no credential), and an attempt to add a server at
`http://169.254.169.254/latest/meta-data/`.

**Say**

* *API keys.* 256 random bits, shown once, stored as a SHA-256 hash and looked
  up on every request, which is why revoking one works on the next call.
* *Upstream credentials.* Encrypted in Postgres with a key that lives in a
  Secret, decrypted only when a request goes to that server, and never returned
  by any API, even to an admin.
* *A member can* call the tools their role allows on each server, create and
  revoke their own keys, and see their own history. *A member cannot* add or
  see the address of a server, see a credential, see anyone else's keys or
  history, or manage people.
* *A malicious or compromised server.* It cannot reach into the cluster, cannot
  be used to reach internal addresses, never receives a client's token or
  another server's credential, cannot shadow another server's tools, and cannot
  stall the others. What it can do is write tool descriptions meant to steer
  the model. Say honestly what limits that (the gateway labels where each tool
  comes from, bounds the description, tells the model to treat it as
  information, and per-server read-only access caps the damage) and what does
  not (nothing confirms a write, and a changed description is not flagged).

Read first: [THREAT-MODEL.md](THREAT-MODEL.md), all of it. It is short and it
is what the questions will be about.

## 5. Chat agent

**Show** the Chat page answering "what orders came in today?", with the tool
chip open, then the Audit log entry with the source "chat".

**Say**

* The loop: send the model the conversation and the tools this user may call;
  if it answers in words, that is the reply; if it asks for tools, run each
  through the gateway, add the results, and ask again. At most eight rounds.
* It acts as the signed-in user because it calls the same code the MCP endpoint
  calls, with that user's identity. Same tools, same permissions, same audit
  log. A disabled server is gone from the chat too.
* The model is reached over an OpenAI-compatible API, so the provider is three
  settings. The key is in a Secret.

Read first: `services/gateway/src/gateway/chat/agent.py`. It is one short file.

## 6. Local to VPS

**Show** `charts/gateway/values-local.yaml` beside `values-prod.yaml`, then
`deploy/sites/example`, then an upgrade and a rollback:

```bash
helm --kube-context k3d-urumi -n mcp-servers history sandbox
helm --kube-context k3d-urumi -n mcp-servers upgrade sandbox charts/mcp-server --reuse-values --set env.DEMO_UPGRADE=yes --wait
helm --kube-context k3d-urumi -n mcp-servers history sandbox
helm --kube-context k3d-urumi -n mcp-servers rollback sandbox <the revision before> --wait
```

**Say**

* The charts are the same. What changes is values: hostnames, TLS on, larger
  volumes, two gateway replicas, where images come from.
* *Domains and ingress.* Locally `*.localhost`, which needs no setup. In
  production real names, HTTPS with certificates from cert-manager, and HTTP
  redirected.
* *Storage.* The cluster's default StorageClass in both; on k3s, `local-path`.
* *Secrets.* Generated by the charts into Kubernetes Secrets and kept across
  upgrades and uninstalls, or supplied by you.
* *Upgrade.* The same `make` command as an install. Image tags are hashes of
  their source, so only what changed is replaced. The gateway rolls with no
  dropped requests; the store restarts, because its volume mounts in one pod.
* *Rollback.* `helm rollback` brings back the previous images and settings. It
  does not reverse database migrations or touch Secrets and volumes.
* Be exact about how far this was tested: rehearsed end to end on a separate
  virtual machine with k3s, production values and HTTPS, not on a rented server
  with a public address. Mention one thing the rehearsal found.
