# Deploying to a VPS, upgrading and rolling back

The same three charts run on the local cluster and on a server. This page says
what differs and how to upgrade.

**Not yet run on a real VPS.** The production values for every chart render and
pass the API server's validation (a server-side dry run), and the local cluster
runs the same k3s version with the same Traefik, storage and network policy
controller. The steps below are what that implies, not a record of a deployment.

## What changes between local and production

Only values, and where images are pushed.

| | Local (`values-local.yaml`) | Production (`values-prod.yaml`) |
|---|---|---|
| Hostnames | `store.localhost`, `gateway.localhost` | Real DNS names pointing at the server |
| TLS | none | `ingress.tls.enabled: true`, certificate from cert-manager |
| URLs the apps believe they have | `http://...` | `https://...`, derived from the same two settings |
| Image registry | `localhost:5001` (in the cluster) | Your registry, for example `ghcr.io/<you>` |
| Volume sizes | 1 Gi | 10 Gi |
| Gateway API replicas | 1 | 2 |
| Stores created in the dashboard | at `<slug>.localhost` | at `<slug>.stores.example.com` (`provisioner.hostTemplate`), each with its own certificate |
| Where the provisioner may reach the Kubernetes API | any private address | the server's address, if it is public (`provisioner.apiServer.cidrs`) |
| Secrets | generated by the charts | generated by the charts, or your own via `existingSecret` |

Storage uses the cluster's default StorageClass in both, which on k3s is
`local-path`. Set `persistence.storageClass` to use another.

## First deployment

1. **A server with k3s.**

   ```bash
   curl -sfL https://get.k3s.io | sh -
   ```

   Copy `/etc/rancher/k3s/k3s.yaml` to your machine as a kube context, replacing
   `127.0.0.1` with the server's address.

2. **DNS.** Point two names at the server, for the store and for the gateway.
   For stores created from the dashboard, also point a wildcard record at it,
   for example `*.stores.example.com`, and set `provisioner.hostTemplate` to
   match. Each new store then gets its own certificate from cert-manager. To
   leave that feature out, set `provisioner.enabled: false`.

3. **cert-manager**, for TLS. Install it and create a ClusterIssuer named
   `letsencrypt-prod` that solves HTTP-01 challenges through the `traefik`
   ingress class. The [cert-manager documentation](https://cert-manager.io/docs/)
   has both steps.

4. **Edit the three `values-prod.yaml` files**: the hostnames, the admin emails.
   If the server's own address is public, put it in the gateway chart's
   `provisioner.apiServer.cidrs` as a `/32`: on k3s the Kubernetes API listens
   on the node's address, and the provisioner's NetworkPolicy must allow it.

5. **Log in to your registry** (`docker login ghcr.io`), then build, push and
   deploy everything:

   ```bash
   make up ENV=prod KUBE_CONTEXT=<context> REGISTRY=ghcr.io/<you> PLATFORM=linux/amd64
   ```

   `PLATFORM` matters when your machine and the server have different CPUs, such
   as an Apple Silicon Mac and an x86 server. If the registry is private, also
   create an image pull secret in each namespace and name it under
   `imagePullSecrets`.

6. **The chat model's key:**

   ```bash
   LLM_API_KEY=<key> make llm-key KUBE_CONTEXT=<context>
   ```

Every `make` target takes `KUBE_CONTEXT`, so the end-to-end checks run against
the server too:

```bash
make smoke KUBE_CONTEXT=<context> STORE_URL=https://store.example.com GATEWAY_URL=https://gateway.example.com
```

## Upgrading

Every image is tagged with a hash of its source, and `make ...-up` passes that
tag to Helm. So an upgrade is the same command as an install, and Helm replaces
only the pods whose image or settings actually changed.

| Component | Command | What happens |
|---|---|---|
| Gateway API | `make gateway-up` | Rolling update. A new pod must be ready for five seconds before an old one stops, and the old one keeps serving briefly after being told to stop. Measured locally: no failed requests during a rollout. New migrations run at startup, one replica at a time. |
| Dashboard | `make gateway-up` | Rolling update of static files. |
| Store's MCP server | `make store-up` | Rolling update. It is stateless. |
| Extra MCP servers | `make mcp-servers-up` | Rolling update. The task list is in memory and is emptied. |
| Store (WordPress, WooCommerce) | `make store-up` | The pod is replaced, not rolled: its volume can be mounted by one pod at a time, so expect about half a minute of downtime. On start the setup container brings WooCommerce up to the version pinned in the image and runs its database migrations. |
| MariaDB, Postgres | change the image tag in values, then the same commands | The pod restarts on the same volume. MariaDB runs its own upgrade step when it meets an older data directory. |

## Rolling back

```bash
helm --kube-context <context> -n gateway history gateway
```

```bash
helm --kube-context <context> -n gateway rollback gateway <revision>
```

The same two commands work for `store` in `store-main`, and for `tasks` and
`sandbox` in `mcp-servers`.

What a rollback does and does not undo:

* **Gateway, dashboard, MCP servers.** The previous images run again. Database
  migrations are not reversed: they are additive, so the previous code keeps
  working against the newer schema. A migration that removes or renames
  something would need the old code retired first.
* **Store.** The previous image runs again, but the setup container never
  downgrades a plugin, and WooCommerce's own database migrations cannot be
  reversed. To go back across a WooCommerce version, restore a database dump
  taken before the upgrade. Take one before any store upgrade:

  ```bash
  kubectl -n store-main exec store-mariadb-0 -- sh -c 'mariadb-dump -u root -p"$MARIADB_ROOT_PASSWORD" --single-transaction wordpress' > store-backup.sql
  ```

* **Secrets and volumes** are never touched by a rollback or by
  `helm uninstall`. Deleting the namespace is what removes them.
